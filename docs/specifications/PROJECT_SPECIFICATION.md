# Project Specification

Normative specification for Repechage's behavior, derived from the build
process and the implemented system. Policy-level rules live in
`backend/GROUND_TRUTH_POLICY.md` (benchmark) and `backend/EXECUTION_POLICY.md`
(execution). Architecture lives in `docs/architecture/`.

## 1. Product scope

Repechage recovers failed Razorpay checkouts:

1. A deterministic detector flags at-risk payments from observed signals.
2. A recovery agent (LLM) reasons over enriched permitted context and
   recommends one of five bounded actions.
3. A deterministic policy gate validates the recommendation.
4. Permitted actions execute as real Razorpay recovery payment links.
5. Webhook-confirmed payments are recorded as recovered revenue.
6. Every step is audited.

Out of scope: charging customers directly (Razorpay Payment Links are the
recovery mechanism), subscription/invoice recovery (planned), multi-merchant
tenancy.

## 2. Payment integration contract

- Orders: created via Razorpay Test Mode (`/transactions/create-test-order`,
  optional `amount_paise`), stored in `transactions`.
- Recovery mechanism: Payment Links only — the Payments API cannot charge a
  customer. Links carry amount, expiry (1 hour), and a reference to the
  transaction.
- Webhooks: `payment_link.paid` / `payment.captured` mark a transaction
  recovered. Signature verified (HMAC); failures return 401 with an audit
  entry. Duplicate deliveries deduplicated on the `X-Razorpay-Event-Id`
  header (primary key of `webhook_events`).

## 3. Detection ruleset

The detector flags a transaction at-risk when, in priority order:

1. `status == "succeeded"` -> not at risk (short-circuits everything).
2. `previous_recovery_attempts >= 3` -> at-risk, tier none
   (`EXHAUSTED_ATTEMPTS`).
3. `status == "failed"` and reason in (network_error, otp_timeout) ->
   at-risk, tier high (`TRANSIENT_FAILURE`).
4. `status == "failed"` and reason in (insufficient_funds, card_declined) ->
   at-risk, tier low (`LOW_RECOVERY_PROBABILITY`).
5. `status == "abandoned_checkout"` -> at-risk, tier high
   (`CHECKOUT_ABANDONMENT`).
6. Otherwise -> not at risk.

Inputs are observed signals only: status, failure_reason,
previous_recovery_attempts (+ amount_paise, previous_successful_payments
selected but unused by the classifier). Enriched context and ground truth
are never read by the detector.

## 4. Benchmark dataset

- 1,000 synthetic events, seed 42, generated by
  `generate_synthetic_data.py`.
- Enriched context columns (tenure, AOV, recency, checkout duration,
  payment method) are materialized at generation time.
- Ground truth (`ground_truth_recoverable`, `ground_truth_outcome`,
  `ground_truth_recovered_amount`) is generated once from a wider signal
  set via tier probabilities (HIGH 0.85 / MEDIUM 0.50 / LOW 0.15 /
  NONE 0.00) — never re-rolled, never exposed at decision time.
- Distribution is recovery-heavy by design (~45-50% recoverable) and is not
  representative of real Razorpay traffic.

## 5. Agent contract

- Input: the six observed detector signals plus enriched context (tenure,
  failed-payment count, AOV, recency, checkout duration, payment method).
  Ground truth is never in the prompt.
- Output (validated against a JSON schema): `diagnosis`,
  `recovery_probability` (0.0-1.0), `recommended_action` (five-value enum),
  `reason`, `confidence` (0.0-1.0).
- Rate limits retried with exponential backoff (2s/4s/8s, max 3). Other
  failures fail fast to a safe escalation decision.
- One decision per event, persisted to `agent_decisions` with
  `decision_path` (ai_decision / pre_filtered / gated_override) and
  `override_reason`.

## 6. Execution contract

- The execution layer acts only on transactions tagged as demo scenarios
  and only when `LIVE_EXECUTION_ENABLED == "true"`.
- Hard stops (never overridden): attempts at cap, transaction already
  recovered.
- Escalations: amount over cap (Rs 5,000), low recoverability tier.
- Volume cap: `MAX_REAL_RECOVERY_ACTIONS` per run.
- Every outcome writes an audit entry with `phase: execution_policy`;
  merchant approvals add `triggered_by: merchant_manual_approval`.
- Repeat runs skip transactions already recovered after an executed action.

## 7. Acceptance criteria (per phase)

| Phase | Exit condition | Verified by |
|---|---|---|
| 0 - API validation | One end-to-end Test Mode transaction: order, payment, webhook, dedup | `tests/test_phase0.py` |
| 1 - Benchmark | 1,000 events, detector metrics, revenue at risk | `backend/reports/baseline.md` |
| 2 - Agent evaluation | Full 662-event agent run vs benchmark under fixed economics | `backend/reports/agent_performance_result.md` |
| 3 - Execution | Real Test Mode recovery loop through the policy gate, audited | `agent_recommendation` / `execution_*` audit entries |
| 4 - Dashboard | Judge understands the product within 30 seconds | landing + dashboard + analytics + audit pages |

## 8. Evaluation rules (summary)

- Recovery attempt = recover_now / send_payment_link / wait_and_retry.
  stop / escalate_to_merchant are excluded from success/failure accounting.
- Attempted recovery on a ground-truth recoverable event credits the amount;
  on a non-recoverable event it is a bad intervention (Rs 200 flat penalty).
- Ground truth is evaluation-only: never shown to the detector or the agent.
- Full rules: `GROUND_TRUTH_POLICY.md` (normative, with integrity rules).
